\section{Computational Experiments}
\label{sec:experiments}

This section evaluates the proposed method on instances derived from an operating bus network.
We first define the base instance and characterize a representative solution, then evaluate the algorithmic components and scalability, and finally examine sensitivity to problem characteristics.

\subsection{Experimental setup and base instance}
\label{subsec:experimental-setup}
The experiments use instances derived from the Tower Transit bus network in Singapore.
The study network contains 28 routes, 493 physical stations, 625 directed links, and five existing plug-in charging locations, as shown in Figure~\ref{fig:case-study-map}.
The 488 stations without plug-in charging are candidate SWC locations, and all directed links are candidate DWC locations.
The interacting routes and shared charging resources induce the cross-route coupling represented in the operational model.

The base service plan is constructed from official Tower Transit route and timetable data and contains 282 buses (trip chains) and 2,850 scheduled trips.
We form five equally likely service-plan scenarios on the fixed physical network: the base plan, systemwide frequency changes of $-10\%$ and $+10\%$, a 25\% frequency increase on route 984, and a 25\% frequency decrease on route 941.
Trip chains and fleet requirements are reconstructed after each frequency perturbation.
This five-scenario instance is the representative base instance for the analyses below unless otherwise specified.

Table~\ref{tab:base-instance-statistics} summarizes the resulting instance.
The ranges in trip and bus counts show how the service-plan perturbations change the operational problem while the physical network and candidate facilities remain fixed.

Facility and battery capital costs are expressed as representative-day equivalents so that they are comparable with daily charging costs.
Unless otherwise specified, wireless-facility costs are set to three times the base values reported with the remaining physical and economic parameters in Appendix~\ref{app:computational-parameters}.

The algorithms are implemented in C++ using Gurobi 12.0.3 and run on an Intel Core i5-14600K processor with 32 GB of memory under a 12-thread budget.
Each run has a 7,200-second time limit; restricted masters and exact scenario MIPs are solved with zero solver gap, and both the Phase~1 switching tolerance $\varepsilon_1$ and the final outer tolerance $\varepsilon$ are set to $10^{-4}$ (0.01\%).
Our code and data are available in the GitHub repository (\url{https://github.com/foangfangkeeke/Two_phase_for_IJOC}).

\subsection{Algorithmic performance and scalability}
\label{subsec:algorithmic-evaluation}

This section first uses an ablation comparison to identify the contribution of the proposed algorithmic components and then examines computational performance as network size and scenario count increase.
We denote an instance by $N$-$k$, where $N\in\{\mathrm{S},\mathrm{M},\mathrm{B},\mathrm{L}\}$ indicates increasing network size, with $\mathrm{B}$ denoting the base network mentioned in Section~\ref{subsec:experimental-setup}, and $k$ is the number of service-plan scenarios.
For example, B-5 denotes the base network with five scenarios.

We use EF for the extensive-form formulation and ILS for the natural integer L-shaped method.
In the remaining method names, L denotes the variable-lifted reformulation, M denotes the monotonicity-strengthened cuts, and 2P denotes the two-phase separation scheme.
The resulting variants are EF, ILS, L-ILS, L-ILS-M, L2P-ILS, and Full, where Full combines all components mentioned above.
In particular, ILS versus L-ILS isolates lifting, while the remaining matched pairs identify the effects of two-phase separation and monotonicity strengthening under otherwise identical configurations.
All decomposition variants use RSP screening, which is held fixed rather than treated as an ablation component.
