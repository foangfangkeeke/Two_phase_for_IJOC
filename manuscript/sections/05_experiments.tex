\section{Computational Experiments}
\label{sec:experiments}

This section evaluates the proposed method on instances derived from an operating bus network.
We first define the base instance and characterize a representative solution, then examine computational sensitivity to problem characteristics and evaluate the algorithmic components and scalability.

\subsection{Experimental setup and base instance}
\label{subsec:experimental-setup}
The experiments use a study network based on the Tower Transit bus network in Singapore.
The network comprises 28 routes, 493 physical stations, 625 directed links, and five existing plug-in charging locations, as shown in Figure~\ref{fig:case-study-map}.
The interacting routes and shared charging resources induce the cross-route coupling represented in the operational model.

\begin{figure}[!htbp]
    \centering
    \includegraphics[width=0.8\linewidth]{figures/study_case.png}
    \caption{Spatial distribution of the Tower Transit bus network used in the case study.}
    \label{fig:case-study-map}
\end{figure}

The base service plan is constructed from official Tower Transit route and timetable data and contains 282 buses and 2,850 scheduled trips.
Two additional service scenarios are generated by decreasing and increasing systemwide route frequencies by 10\%, with trip chains and fleet requirements recomputed accordingly.
The three scenarios are equally likely.
Other physical and economic parameters and their sources are reported in Appendix~\ref{app:computational-parameters}.

The algorithms are implemented in C++ using Gurobi 12.0.3 and run on an Intel Core i5-14600K processor with 32 GB of memory under a 12-thread budget.
Each run has a 7,200-second time limit and uses the outer termination tolerance $\varepsilon=10^{-4}$.
Our code and data are available in the GitHub repository (\url{https://github.com/foangfangkeeke/Two_phase_for_IJOC}).

\subsection{Representative planning solution}
\label{subsec:solution-characteristics}

We use the base instance to characterize a representative solution and compare it with a controlled benchmark without WPT.
The benchmark disables SWC and DWC while retaining the same service scenarios and plug-in charging resources and reoptimizing the scenario-dependent battery configurations and charging operations.
This comparison assesses whether allowing WPT investment produces a nontrivial substitution among infrastructure, battery, and charging decisions.

Relative to the no-WPT benchmark displayed in Table~\ref{tab:representative-cost-breakdown}, the WPT solution adds \$192.240 per day in facility cost and \$917.451 per day in charging cost while reducing battery cost by \$3,327.040 per day.
The reported objective decreases by \$2,217.349 per day, or 21.98\%.
The comparison indicates that the model substitutes wireless-facility investment and additional charging expenditure for substantially lower battery expenditure.

The battery configurations reflect the same substitution.
With WPT, all 28 routes choose the 20-kWh option in every scenario; without WPT, only eight routes select the 20-kWh option in each scenario, the mean route battery capacity ranges from 82.86 to 85.71 kWh, and the maximum is 310 kWh.
The representative plan selects 84 of the 488 candidate SWC stations and two of the 625 candidate DWC links.

This pattern is consistent with WPT investment being concentrated at relatively high-exposure locations.
Overall, the benchmark comparison shows that allowing WPT produces a nontrivial joint planning response: the additional infrastructure and charging expenditures are offset by substantially lower battery expenditure, while the selected wireless facilities are actively used across the service scenarios.

\subsection{Algorithmic evaluation}
\label{subsec:algorithmic-evaluation}

The algorithmic evaluation considers method components, network size, and scenario count while holding RSP screening fixed within the two-phase methods.
An instance is denoted by $N$-$k$, where $N\in\{\mathrm{S},\mathrm{M},\mathrm{B},\mathrm{L}\}$ identifies the small, medium, base, or large network and $k$ is the number of service-plan scenarios.
